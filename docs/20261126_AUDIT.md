review of the first data-loss fixes: Phases 2, 3 and 4 of the transfer fix
path, and the fixes made after the review of Phase 1. This file lists every

## A. Files left in the wrong state

### A1. A move deletes its source after the source's streams failed to copy

* **Severity:** data loss (the source's alternate data streams, among them the download mark). The file's own bytes are not lost.
* **Commit:** `2b299bc`.
* **Where:** `crates/simplefile-service/src/progress/execute.rs:419` and the helper `copy_alternate_streams` at `execute.rs:503-519`; `crates/simplefile-core/src/file_ops/metadata_preserve.rs` (`copy_alternate_streams`, `alternate_stream_names`, `copy_stream`).
* **What goes wrong:** every failure to copy a stream is only written to `service.log`. The file is then given its name, and in a move the source is deleted, with its streams.
* **When it happens:** the roadmap names only destinations that cannot hold streams. It also happens when:
  * reading `source:Zone.Identifier` is refused: a sharing violation or access denied, for example an antivirus scan or a browser still writing the stream;
  * the disk fills while a stream is written, which also leaves a cut stream on the copy;
  * a file has more streams than the 1 MiB list buffer holds.
* **Scenario:** move a downloaded installer to another drive while an antivirus holds its `Zone.Identifier` stream. The copy has no mark, the source is deleted, and the installer then runs without the warning Windows would have shown.
* **Proposed fix:** in a move, make any stream failure other than "the destination cannot hold streams" fail the file as a retryable error, so the source is kept. Tell that one case apart by the error from creating the destination stream (`ERROR_INVALID_PARAMETER`, `ERROR_NOT_SUPPORTED` or `ERROR_INVALID_NAME` on FAT and some shares), or by asking the destination volume for `FILE_NAMED_STREAMS` once per pass. A copy keeps its source, so for a copy logging stays enough.

### A2. A failed move whose source changed size leaves a damaged file at the destination

* **Severity:** wrong state on disk. The source is kept.
* **Commit:** `5413d34`.
* **Where:** `crates/sumafile-transfer/src/journal.rs`: `StagingLease::abort` (`:359-363`) calls `recover`, and `Unsettled::reclaim` (`:781-789`) does too; `is_only_copy` (`:932-941`); `keep_only_copy` (`:960` onwards). The failures come from `execute.rs:1272` and `:1406-1425`.
* **What goes wrong:** since `5413d34`, "the source is there" means "a file of the recorded length is at the source path". That rule is meant for recovery after a crash, but `abort` runs it during a live pass, while the source is in place. A source that changed size during the copy is then taken for gone, and the partial or direct-written file is treated as the only copy.
* **Scenarios:**
  * **"Write directly" on, the source grows** (a log, a download in progress). The copy writes the recorded length and fails with "Source changed during transfer". `keep_only_copy` finds a file of full length that is not hidden, takes it as complete and returns; `finish` removes the record. The move is reported as failed, and a copy that may mix old and new bytes stays under the final name with no record.
  * **The source shrinks** ("Source became shorter"). The copy is short, so `keep_only_copy` keeps it with its record. Every later visit to the folder sees a source of another length and keeps it again: it is never cleaned up.
  * **Default staged copy.** The partial file is still hidden, so it is kept, and its line stays in the record for good.
  * **Message:** in the last two cases the error says "The source of a moved file is gone; its copy is kept at …" while the source is still there.
* **Related:** a direct-written file is never hidden, and a copy in several streams reaches full length with its first range. After a crash in which the source's length changed or the source was deleted, such a file can be taken as complete while it still has holes.
* **Proposed fix:**
  * Give `abort` and `Unsettled::reclaim` a cleanup that skips the only-copy rule. In a live pass the move has not deleted its source, so the partial file is disposable.
  * Keep the rule for recovery of records found when a folder is visited.
  * For a file a move writes directly, do not take "full length and not hidden" as complete: keep such a file and its record, and report it, rather than give it its final name.

### A3. "Write directly" asks for delete access on the destination

* **Severity:** wrong state on disk (the transfer fails). A regression.
* **Commit:** `3f6008c`.
* **Where:** `crates/sumafile-transfer/src/journal.rs:404`, `open_staged`, which sets `access_mode(GENERIC_WRITE | DELETE)` for every call, including the direct write where the staged path is the destination. The FTP/SFTP plugin's direct download uses the same call.
* **What goes wrong:** delete access is there so that a partial file can be renamed through its handle. A direct-written file is never renamed, but asks for it all the same.
* **Scenario:** a share or folder where users may create and write files but not delete them: a drop box, or an inherited "Deny Delete" entry. "Write directly" was the one setting that worked there, because a staged copy needs delete access for its rename. Every file now fails at create with "Access is denied". As a side effect, while the file is open, other programs that open it without sharing delete access are refused.
* **Proposed fix:** ask for `DELETE` only when the file is a partial file under a temporary name (`hidden` is set). Optionally retry a create refused for access without `DELETE`, and rename by path afterwards.

### A4. A Replace move into a mounted volume fails instead of being copied

* **Severity:** wrong state on disk (the item fails).
* **Commits:** `023063d` and older code.
* **Where:** `crates/simplefile-service/src/progress/execute.rs:1538-1571` (`move_by_rename`), `crates/sumafile-transfer/src/reliability.rs:176-189` (`classify_io`).
* **What goes wrong:**
  1. When the same-volume check is wrong, the first rename fails with `ERROR_NOT_SAME_DEVICE` (17).
  2. The destination exists, so `path_exists_no_follow(&dst)` sends the item into the Replace branch.
  3. `swap_source_into_place` moves the existing file aside, the second rename fails with 17, and the original is put back.
  4. Error 17 is classified as permanent, so the item fails with "Finalize destination (original destination was restored)". It is never copied.
* **When it happens:** a volume mounted in a folder (`C:\Data\Archive`), a DFS namespace, or a `subst` or mapped letter changed within the one-minute cache.
* **Scenario:** volume E is mounted at `C:\Data\Archive`. Move `C:\Users\me\a.txt` into it with Replace while `a.txt` exists there: the move fails, although the transfer guide says the item is copied.
* **Proposed fix:** in `move_by_rename`, answer error 17 from the first rename with `None` ("copy instead"), before the Replace branch.

### A5. Records of an interrupted 1.1.5 "Write directly" copy are not recognised

* **Severity:** compatibility; wrong state on disk after an upgrade.
* **Commit:** `bc06343` (incomplete), with `3aa5e2f` as the cause.
* **Where:** `crates/sumafile-transfer/src/journal.rs:1176-1196` (`recover_directory`), `crates/sumafile-transfer/src/staging.rs` (`staging_path_with_salt`).
* **What goes wrong:**
  * A file written directly has an own record named after `staging_path_for(destination, "ownership")`.
  * Version 1.1.5 hashed that name with `DefaultHasher`. Commit `3aa5e2f`, after 1.1.5, changed it to FNV-1a.
  * `recover_directory` accepts an own record only when `record_path(&last.staged)` equals the record's path, so a 1.1.5 direct-write record falls to `Some(_) => continue`.
  * `bc06343` made the 1.1.5 file-identity format readable, but not this name. Records of staged copies are found, because their name is the partial file's name plus `.state`, whatever the hash.
* **Scenario:** a 1.1.5 copy with "Write directly" on (also over an existing file, which 1.1.5 still allowed) is interrupted, and the user upgrades. 1.1.5 would have deleted the half-written file on its next visit; this version leaves it under its real name, and the record stays for good.
* **Proposed fix:** also accept an own record whose staged path equals its destination, lies in the folder (`within`), and whose file name is `.<destination name>.<16 hex digits>.sumafile-partial.state`. Add a test that writes such a record with the 1.1.5 name and identity.

### A6. A hidden file a move wrote directly keeps its record forever after an interruption

* **Severity:** wrong state on disk (a record kept, a warning logged on every visit).
* **Commit:** `aa2f277`.
* **Where:** `crates/sumafile-transfer/src/journal.rs:957-969` (`keep_only_copy`).
* **What goes wrong:** a copy now keeps the source's Hidden attribute. `keep_only_copy` takes a file that is still hidden as incomplete, and so returns an error for a complete file a move wrote directly. The record is kept, and every later visit to the folder logs a warning.
* **Scenario:** a power loss after a move deleted a hidden source but before the removal of the record reached the disk. Rare.
* **Proposed fix:** record in the move's line whether the source was hidden, and for such a file judge completeness by the recorded length and the record's state, not by the attribute. Until then, correct the guide (see [I9](#i-documents-that-say-what-the-code-does-not-do)).

### A7. A retried "folder into itself" creates a folder in its source before it is refused

* **Severity:** wrong state on disk (an empty folder left in the source).
* **Commit:** `5413d34`.
* **Where:** `crates/simplefile-service/src/progress.rs:412` (`create_dir_all(parent)`), now before `ensure_dir_not_inside_itself` at `:468`.
* **Scenario:** a retried item that moves `A` into `A\sub\A` creates `A\sub` inside the source and is then refused.
* **Proposed fix:** create the parent only after the checks; recovery needs the folder only when it exists already.

## B. Undo, Redo and the operations journal

### B1. Undo and Redo take "could not check" for "gone"

* **Severity:** wrong result (Undo reports success and leaves files behind).
* **Commit:** `ea920f5`.
* **Where:** `src-winui/SimpleFile.Core/MergeTransferUndo.cs:110`, `:162`, `:197`, `:248`; `src-winui/SimpleFile.Core/NativePath.cs:14-30` (`ExistsNoFollow`); also `UndoStack.PushCopy`, `PushMove` and `PushCreate`.
* **What goes wrong:** `ExistsNoFollow` is a bare `GetFileAttributesW` and returns false on any error: access denied, a share that is offline, or a path longer than 260 characters. The app's manifest does not declare long-path awareness, so a long path without `\\?\` always fails there. The Rust service handles such paths, because `std` adds the prefix.
* **Scenario:**
  1. The user copies or moves a project folder with a deep `node_modules` into an existing folder.
  2. Ctrl+Z: every file whose destination is longer than 260 characters counts as already undone, and no request is sent for it. Undo reports "Undid: Move N items" while those files stay at the destination.
  3. Redo of those files then fails every time ("could not be moved again").
  The same happens with a destination share that is offline.
* **Proposed fix:**
  * Add a three-way check, `NativePath.Existence(path)` returning exists, missing or unknown. Prefix absolute paths with `\\?\` (or `\\?\UNC\`), and answer missing only for `ERROR_FILE_NOT_FOUND` and `ERROR_PATH_NOT_FOUND`.
  * Let Undo and Redo skip a file only when it is missing.
  * Better still, have the service report per-file outcomes for the batch, and count as done only what it reports.

### B2. Undo, Redo, Undo of a copy skips files after a partial failure

* **Severity:** wrong result (a copy is left behind; or Undo removes nothing and reports success).
* **Commit:** `ea920f5`.
* **Where:** `src-winui/SimpleFile.Core/UndoStack.cs:55-91` (`PushCopy`, the `removed` array).
* **What goes wrong:** `removed[]` is set by an Undo that failed, and Redo never resets it.
* **Scenario:**
  1. Copy `a.txt` and `b.txt`, and press Ctrl+Z while the copy of `b.txt` is locked: `a.txt` is trashed, `removed` becomes `[true, false]`, and the Undo fails.
  2. Close the program holding `b.txt` and press Ctrl+Z again: `b.txt` is trashed and the Undo succeeds.
  3. Ctrl+Y copies both again.
  4. Ctrl+Z trashes only `b.txt`; the new copy of `a.txt` stays.
  When every copy was marked removed, `TrashAsync([])` succeeds and removes nothing.
* **Proposed fix:** clear `removed` at the start of Redo, or mark each copy Redo recreates as not removed.

### B3. A batch that fails partway loses what it did

* **Severity:** wrong state on disk (a Redo that can never complete; copies left in the Recycle Bin).
* **Commit:** `ea920f5`.
* **Where:** `src-winui/SimpleFile.Core/MergeTransferUndo.cs:150-153`, `:183-186`, `:217-229`; `crates/simplefile-core/src/recycle_bin.rs:57-62` (`restore_recycle_bin`); `move_to_trash` in `crates/simplefile-core/src/file_ops.rs`.
* **What goes wrong:**
  * **Restore:** `restore_recycle_bin` stops at the first failure and returns an error, with the earlier files already restored. `RestoreBatchAsync` marks none of them. On the next Redo the first restored file meets "The destination already exists" and the step fails. That Redo can never complete, and a Redo entry cannot be dropped. Before batching, each restored file moved the step on.
  * **Trash:** `move_to_trash` returns an error without paths when any one file fails. Every file of the batch (up to 499) is left with `RecyclePath = null`. Redo then copies them again from their sources, which may have changed or gone, and the old copies stay in the Recycle Bin.
* **Proposed fix:**
  * Have both service calls return a result per path. Mark what was done before the step fails.
  * For restore, also count a file as restored when its destination exists now and the Recycle Bin item is gone.

### B4. Redo's test for "done" is wrong both ways

* **Severity:** wrong result (a file the user made can be trashed later; a Redo that never completes).
* **Commit:** `ea920f5`.
* **Where:** `src-winui/SimpleFile.Core/MergeTransferUndo.cs:197-201`, `:246-252`.
* **What goes wrong:**
  * **A file the user put there counts as done.** `Undone = !Exists(Destination)` holds even when the call failed with a conflict, caused by a file the user created at that path between Undo and Redo. The first Redo fails with the conflict, a second Redo succeeds, and the next Undo trashes the user's own file (in the copy case).
  * **A gone source never counts as done.** When the source is gone and the destination missing, the file fails in every pass, so the Redo is stuck. The class comment and the commit message say that a file no longer where the step would take it from counts as done.
* **Proposed fix:** count as done only what the service reports as committed. Treat a conflict as not done. Skip a file whose source is missing, and say so in the step's message.

### B5. A move-Undo batch can take one file of the next item

* **Severity:** wrong result.
* **Commit:** `ea920f5`.
* **Where:** `src-winui/SimpleFile.Core/MergeTransferUndo.cs:121-122`.
* **What goes wrong:** the batch boundary is checked after a file is added. The first file of the next transferred item goes out in the previous item's batch, under that item's `PassFolder`. That folder decides the service's recovery of the destination root, the pass's network flag and the journal's destination. Redo (`:204-208`) checks before it adds.
* **Proposed fix:** send the batch when the next file is not of the same root, before `batch.Add(file)`.

### B6. A refresh error after a successful Undo is shown as a failed Undo

* **Severity:** wrong result.
* **Commit:** `ea920f5`.
* **Where:** `src-winui/SimpleFile.App/MainWindow.Transfer.cs:1413`.
* **What goes wrong:** when `RefreshAffectedPanesAsync` throws after `UndoAsync` succeeded, `ShowUndoFailure` says the step "stays the next step to undo". Its **Remove from undo history** button then does nothing, because the step is no longer the next one.
* **Proposed fix:** show `ShowUndoFailure` only for an exception from `UndoAsync` itself; report a refresh failure on its own.

### B7. A failed rotation of `operations.jsonl` drops every later line

* **Severity:** wrong result (the journal stops being written).
* **Commit:** `3b79250`.
* **Where:** `src-winui/SimpleFile.Core/OperationJournal.cs:90`, `:103-111`.
* **What goes wrong:** the rotation `File.Move(..., overwrite: true)` is inside `Append`'s try block. When `operations.jsonl.1` is read-only or locked, the move throws, the line is dropped, and every later line is dropped too once the file is past 4 MiB. A second instance that holds the file loses one line in the same way.
* **Proposed fix:** catch a rotation failure on its own, log it, and append to the current file anyway.

## C. Scheduler and retries

### C1. One file's retries still empty the lane, and a storm halves it only once

* **Severity:** wrong result. The commit, the changelog and the release notes say the opposite.
* **Commit:** `1a2f5c4`.
* **Where:** `crates/sumafile-transfer/src/tuning.rs:901-911` (`Controller::sample`), fed by `crates/simplefile-service/src/progress/parallel.rs:1545-1556` and the forced window close in `Sampler::observe` (`tuning.rs:436-456`).
* **What goes wrong:**
  * `wait_to_retry` counts a retry each time an attempt fails.
  * The attempts are spaced by `Retry::failed_with`: 1, 2, 4, 8, then 16 seconds. With the defaults (10 tries, 1 s wait) that is 9 waits.
  * Any retry closes the measuring window at once, and the window carries only the retries counted since the last pass of the event loop, at most 50 ms before.
  * Between two retries seconds apart, an ordinary window closes, after 1 s with work done or at its 2–5 s cap. That window calls `sample(retries = 0)` and sets `retrying = false`, so the next retry counts as a new bout and halves the lane again.
* **Scenarios:**
  * **One file on a flaky share that fails every try.** Retries land at about 0, 1, 3, 7, 15, 31, 47, 63 and 79 s. From the third on, each starts a new bout: 32 → 16 → 8 → 4 → 2 → 1, and the lane stays at 1 behind a hold that keeps doubling. The old code got there one step sooner.
  * **Many files throttled at once.** Their retries arrive in separate passes of the loop, so a forced window almost never carries two or more. A storm whose retries come less than 1–2 s apart is one bout, and halves the lane once.
* **The tests miss it:** `one_file_retried_again_and_again_halves_the_lane_once` (`tuning/tests.rs:1599`) and the storm test feed back-to-back one-second windows with 1 or 5 retries, which the scheduler never produces.
* **Proposed fix:**
  * Decide bouts by time. A bout lasts until no retry has come for longer than the longest wait between tries (16 s with the defaults; take it from the policy).
  * Count distinct files, not windows. Report the files that retried since the last report rather than a count: one file retried again and again then halves the lane once.
  * Within a bout, halve again when the number of distinct failing files reaches twice what it was at the last halving, or when the bout's retries per second stay above a threshold.
  * Write the tests from the real timing: a file failing at the backoff's intervals with ordinary windows between, and many files failing in separate loop passes.

### C2. The setting recorded before the retries can be a probe

* **Severity:** wrong result (a good setting is never saved; saved values can only rise).
* **Commit:** `1a2f5c4`.
* **Where:** `crates/sumafile-transfer/src/tuning.rs:909` (`before_retries.get_or_insert(self.concurrency)`) and `:1151` (`learned_concurrency`).
* **What goes wrong:** the value recorded is the one the lane runs at when the first retry comes, which can be an upward probe.
* **Scenario:** the lane's best is 32 and it probes 48. The provider throttles, retries arrive, 48 is recorded and the lane halves to 24. It later settles at 32 or 36. `learned_concurrency` asks for at least 48 and saves nothing, and the next transfer on the route goes through it all again. On a route that sees any retry, only values at or above the starting value are ever saved.
* **Proposed fix:** record `best_concurrency`, the settled value before the probe. At that point in `sample` it has not yet been overwritten.

### C3. A settings change during a task forgets the retry baseline

* **Severity:** wrong result (the old bug comes back after a settings change).
* **Commit:** `1a2f5c4`.
* **Where:** `crates/sumafile-transfer/src/tuning.rs:838-846` (`update_policy`).
* **What goes wrong:** the controller is rebuilt when the mode, the ceiling or the Custom count changes. The rebuild carries `retry_bouts` over, but not `before_retries` or `retrying`.
* **Scenario:** retries take the lane from 32 to 4, and the user changes Transfer defaults during the task. At the end the lane saves 4 for the route.
* **Proposed fix:** carry both fields across the rebuild.

## D. Progress readout

### D1. A pass after Retry counts skipped and already-copied files as speed

* **Severity:** wrong result.
* **Commit:** `8ecf375`.
* **Where:** `src-winui/SimpleFile.Core/TransferProgressAccumulator.cs:136-147` (`Apply`), called from `src-winui/SimpleFile.App/MainWindow.Transfer.cs:394`.
* **What goes wrong:** once the accumulator carries an earlier pass, `Apply` builds a new `ProgressUpdate` and does not copy `Untransferred`, which then arrives as 0. Offsets are set in every pass after Retry or a conflict answer (`CompletePass`), and in the first pass when conflicts were decided before it (`SeedPreDecidedConflicts`).
* **Scenario:** a move fails on a few files and the user chooses Retry. In the new pass each file recognised as already copied adds its whole size to the bytes done, and that counts as speed: gigabytes a second and a time remaining that makes no sense. A file is recognised as already copied only in a retry pass, so that part of the change never works in the app.
* **Proposed fix:** copy `Untransferred = update.Untransferred` in `Apply` (or the measure that replaces it, see [D8](#d8-copying-a-set-aside-file-again-reads-as-stalled)), and add an accumulator test.

### D2. Slow transfers read as stalled, then show a speed several times too high

* **Severity:** wrong result. A regression.
* **Commit:** `8ecf375`.
* **Where:** `src-winui/SimpleFile.Core/TransferProgressRateTracker.cs:70-81`, with `PROGRESS_BYTE_STEP` (4 MiB) in `crates/simplefile-service/src/progress/reporting.rs:8` and the per-file reports at `execute.rs:615-622`, `:851-858` and `:1049-1056`.
* **What goes wrong:**
  * A file's bytes reach the readout in steps of 4 MiB. The app gets an update every 200 ms, but with the same bytes done until the next step.
  * Below about 1.3 MiB/s a step takes more than 3 seconds, so the stall rule fires between any two steps. It clears the speed and moves the sample time to that moment.
  * The next step is then divided by the time since that moment only.
* **Scenario:** one large file to a share at 1 MiB/s, or any transfer with a bandwidth limit under about 1.3 MiB/s:
  * at 3 s the row reads "Calculating speed";
  * at 4.2 s it reads 4 MiB / 1.2 s ≈ 3.3 MB/s, 3.5 times too fast, with a time remaining 3.5 times too short;
  * at 7.2 s it reads "Calculating speed" again, and so on.
  At 0.25 MiB/s the reading is up to 16 times too fast. After a real stall, the first sample can include up to 3 s of waiting, so the speed reads too low for about 1.5 s.
* **Proposed fix:**
  * In the service, also report a file's bytes when 500 ms have passed since its last report and its bytes changed, in all three copy loops, so that nothing new for 3 seconds really means a stall.
  * In the app, do not move the sample time on a stall; only hide the speed.

### D3. Time remaining is far too long in a merge that skips most files

* **Severity:** wrong result.
* **Commit:** `8ecf375`.
* **Where:** `src-winui/SimpleFile.Core/TransferProgressFormatter.cs:274`.
* **What goes wrong:** time remaining is `(Total - Current) / speed`. The speed now leaves out the bytes that were not transferred, but `Total - Current` still holds the bytes that will be skipped or renamed later, which take no time.
* **Scenario:** a 1 TB merge in which 990 GB is already at the destination, the rest copied at 100 MB/s. Early on the row reads "2h 40m remaining" for a pass that ends in minutes.
* **Proposed fix:** compute the time remaining from a moving rate of all bytes done (`Current`, skipped and renamed bytes included). Keep the transferred-bytes rate for the speed text only.

### D4. "Finishing" for the last file lasts at most 200 ms

* **Severity:** wrong result; the guide says otherwise.
* **Commit:** `8ecf375`.
* **Where:** `crates/simplefile-service/src/progress/parallel.rs:1245-1257` (forwarding) and `:1566-1580` (the loop's "running" updates).
* **What goes wrong:** after the coordinator forwards the last file's "finalizing", its loop keeps sending "running". It wakes every 50 ms and sends every 200 ms, and again when no file is active. Nothing in the app keeps the finalizing state.
* **Scenario:** a move of one 4 GB file to a USB stick, where a move always flushes. "Finishing" shows for at most 200 ms. During the rest of the flush, the rename and the source's deletion, the row reads "Moving 1 item 100%", and after 3 s "Calculating speed". For a small last file the row goes finishing, running, finishing.
* **Proposed fix:** once the task's finalizing has been forwarded, send "finalizing" instead of "running" until another file is dispatched or a file is queued again.

### D5. With one file at a time, skipped, renamed and already-copied files are never named

* **Severity:** wrong result; the guide and the changelog say otherwise.
* **Commit:** `8ecf375`.
* **Where:** `crates/simplefile-service/src/progress/parallel.rs:1562-1564` (`last_item`).
* **What goes wrong:**
  * `last_item` is set only from a file still active after the loop has read its messages.
  * A skipped, renamed or already-copied file, and a link, sends no progress message: only `Finished`, which removes it in the same pass of the loop.
  * `last_item` starts empty, and a first file whose finalizing and `Finished` are read together is not named either.
* **Scenario:** Automatic mode on a hard disk with large files runs one file at a time. In a same-drive merge move, where every file is renamed, or a merge copy with Skip, `last_item` stays at the last copied file. When none was copied yet it stays empty, and the window shows "Preparing transfer" for the whole run, which is the defect the commit says it fixed. The new test (`progress.rs:2597-2606`) copies only tiny regular files, and can fail on a slow machine.
* **Proposed fix:** set `last_item` when a file is dispatched, and from the removed file's path in the `Finished` handler.

### D6. Bytes not transferred can run ahead of bytes done

* **Severity:** wrong result (a dip, then a spike in the speed; a leak after a failed delete).
* **Commit:** `8ecf375`.
* **Where:** `crates/simplefile-service/src/progress/parallel.rs:774`, `:785` (worker side), against `:1271` (coordinator side).
* **What goes wrong:** for a renamed or already-copied file, the worker adds to the shared counter before it sends `Finished`. The coordinator adds the bytes to `result.bytes` only when it handles `Finished`, and `emit_now` reads the counter after it has computed bytes done.
* **Scenario:** a merge move where some renames fall back to copying. An update sent in that window has transferred bytes lower by the file's size, so the app's tracker resets. The next sample then adds the whole size, and a 50 MB renamed file reads as about 125 MB/s. The already-copied path deletes the source inside the window too (`:815`). When that delete fails for good, the size stays in the counter, while the file counts as failed with 0 bytes.
* **Proposed fix:** do this accounting in the coordinator, when the outcome arrives (a flag on the outcome, or the bytes carried in `Message::Finished`), so that bytes done and bytes not transferred change in one step. The measure proposed in D8 removes the problem altogether.

### D7. "Finishing" shows while a file waits for its retry round

* **Severity:** wrong result (the row flickers).
* **Commit:** `8ecf375`.
* **Where:** `crates/simplefile-service/src/progress/parallel.rs:1245-1248`.
* **What goes wrong:** the condition `active.len() == 1 && producer_done && ready_empty` does not look at `deferred_retries`.
* **Scenario:** file B fails with a transient error and is set aside. The last other file finalizes, so the row reads "Finishing". Then B's round starts and the row reads "Copying" again.
* **Proposed fix:** add `&& deferred_retries.is_empty()`.

### D8. Copying a set-aside file again reads as stalled

* **Severity:** wrong result; the guide says otherwise.
* **Commit:** `8ecf375`.
* **Where:** `crates/simplefile-service/src/progress/parallel.rs:1240` and `:1429`.
* **What goes wrong:** when a set-aside file's new round starts, its line starts at the bytes it had reached, and `max` keeps it there until the new copy passes them. Bytes done stay flat while bytes are written.
* **Scenario:** an 8 GB file fails at 7 GB and is copied again at 100 MB/s. For about 70 s the row reads "Calculating speed" and "Estimating time" while data moves. Before this commit the last speed stayed.
* **Proposed fix:** measure the speed on a count of bytes actually written in the pass, which only grows. Send it in place of `untransferred` (frame version 3 is not released, so its field can still change), and let the app take the speed from its change. This also removes [D6](#d6-bytes-not-transferred-can-run-ahead-of-bytes-done).

### D9. The "Finishing" update leaves out the bytes of failed files

* **Severity:** wrong result (the bar goes back while the folders' times are set).
* **Commit:** older code, kept on screen by `8ecf375`.
* **Where:** `crates/simplefile-service/src/progress/parallel.rs:598-600` and `:646-652`.
* **What goes wrong:** `copy_selection` passes `*completed_bytes`, which holds the bytes of copied and skipped files but not `failed_bytes`. The running updates and the final error update include them.
* **Scenario:** a tree copy in which one file fails for good after 900 MB. During "Finishing", bytes done drop by 900 MB, and the final error update puts them back.
* **Proposed fix:** pass `*completed_bytes + copy_res.failed_bytes`.

### D10. Details can freeze on files that are done

* **Severity:** wrong result (minor).
* **Commit:** `8ecf375`.
* **Where:** `crates/simplefile-service/src/progress/parallel.rs:1576`.
* **What goes wrong:** an empty list of active files is no longer sent. When no file is active in the middle of a pass, because the folder scan is slower than the copy, the last list (finished files at, say, 87%) stays in Details until the next file starts.
* **Scenario:** a share with a deep tree of mostly empty folders.
* **Proposed fix:** when the list empties in the middle of a pass, send the files that finished at their full size, or send an empty list after a short delay.

### D11. A frame-version mismatch drops the connection

* **Severity:** compatibility (low).
* **Commit:** `8ecf375`.
* **Where:** `src-winui/SimpleFile.Ipc/BinaryFrameCodec.cs:21-24`, `src-winui/SimpleFile.Core/BackendSession.cs:320`; `ipc/schema/v1/goldens/ipc.handshake.result.json`.
* **What goes wrong:**
  * The app rejects another frame version by throwing in the decoder. Nothing catches that, so the receive loop ends with "IPC pipe closed", on the first binary frame, usually a directory listing.
  * The handshake reports `binaryFrameVersion`, but the app never compares it with its own.
  * Nothing ties `protocol.json`'s `binaryFrames.version` to either constant, and the handshake golden still says 1.
* **Scenario:** in a release the app starts the service it ships with, so this does not happen. In a development checkout, where the app can start a stale service build, it fails with an unclear error and may reconnect in a loop.
* **Proposed fix:** compare `binaryFrameVersion` after the handshake. Fall back to JSON frames when it differs, or fail with a message that names both versions. Update the handshake golden, and make `scripts/check-ipc-schema.mjs` check the version against both constants.

## E. Bandwidth limit

### E1. The shared limit is split by copy threads, not by task

* **Severity:** wrong result.
* **Commit:** `fbd45fe`.
* **Where:** `crates/sumafile-transfer/src/resources.rs`: `Pacer::wait_turn` (only the head of the line takes credit) and `RateLimit::wait` (each turn waits in the group's line).
* **What goes wrong:** each copy thread holds its own ticket in the group's line, which serves strictly in turn, so a task's share grows with the number of tickets it has waiting.
* **Scenario:** two tasks limited to 10 MiB/s. Task A copies small files with four threads; task B copies one large file to a share in one stream. A gets about 8 MiB/s and B about 2.
* **Proposed fix:** give the group's line one place per task, served in turn. Each task then hands its turn to its own threads through its own line.

### E2. The bandwidth group keeps an entry for every finished task

* **Severity:** wrong result (a slow leak).
* **Commit:** `fbd45fe`.
* **Where:** `crates/sumafile-transfer/src/resources.rs`: `RateGroup::bytes_per_second` (the only place dead entries are removed) and `RateLimit::in_group`.
* **What goes wrong:** `in_group` always adds an entry, but dead entries are removed only when a limited task waits in the group. With the default of no limit that never happens. Each dead entry keeps its limiter's memory, about 200 bytes, for the life of the service, and of the FTP/SFTP plugin.
* **Proposed fix:** remove dead entries in `in_group` before adding.

## F. Attributes, streams and names

### F1. One refused attribute leaves the copy hidden

* **Severity:** wrong result (a copy of a visible file is hidden).
* **Commit:** `aa2f277`.
* **Where:** `crates/simplefile-core/src/file_ops/metadata_preserve.rs:125-151` (`apply_basic_metadata_to_handle`).
* **What goes wrong:** the fallback is all or nothing. When the destination refuses one of the carried bits (System, not-indexed), both the full call and the attributes-only call fail, and the copy keeps its partial file's Hidden attribute. The roadmap says this needs both times and attributes refused; one refused attribute is enough.
* **Scenario:** a drive with indexing turned off, where every file has the not-indexed attribute, copied to a share that refuses that bit. FAT and exFAT are said to drop unknown bits without an error; other servers were not checked.
* **Proposed fix:** when the attributes are refused, set again with the destination's own attributes without Hidden, as `staging::clear_hidden` does. Then try read-only alone, and log what was not kept.

### F2. An FTP/SFTP download fails when its Hidden attribute cannot be cleared

* **Severity:** wrong state on disk (the download fails on every try).
* **Commit:** `aa2f277`.
* **Where:** `plugins/remote/backend/src/transfer.rs:999-1007`.
* **What goes wrong:**
  * A `clear_hidden` error fails the attempt, so every retry fails the same way and the download is lost. A local copy only logs the same refusal.
  * It also runs before the checksum check and the check that the remote file did not change. When either fails, the retry writes into a partial file that is no longer hidden.
* **Proposed fix:** log a refusal instead of failing, and clear the attribute after the checks, just before the file gets its name.

### F3. Temporary names can pass 255 bytes on a NAS

* **Severity:** wrong state on disk (the file cannot be copied).
* **Commit:** `fb6c9e0`.
* **Where:** `crates/sumafile-transfer/src/staging.rs:1047-1080` (`name_units`, `fitted_name`).
* **What goes wrong:** on Windows names are fitted in UTF-16 units. A share served by a NAS from ext4 or btrfs limits names to 255 bytes.
* **Scenario:** a name of 80 CJK characters is 240 bytes and fits on the NAS. Its partial name is 275 bytes and is refused, so the file still cannot be copied.
* **Proposed fix:** fit temporary names to 255 UTF-16 units and to 255 UTF-8 bytes, whichever is shorter.

### F4. `preserve_basic_metadata` would change a link's target

* **Severity:** wrong result (latent: no caller passes a link today).
* **Commit:** `aa2f277`.
* **Where:** `crates/simplefile-core/src/file_ops/metadata_preserve.rs:4-28`.
* **What goes wrong:** the comment still says the function is for "directories and symlinks". The Windows version opens without `FILE_FLAG_OPEN_REPARSE_POINT`, and `fs::metadata` follows links, so for a link it would set the target's times, read-only, Hidden and System. Only `parallel.rs:682` calls it, for folders.
* **Proposed fix:** correct the comment to say folders. If a link caller is ever added, open the link itself with `FILE_FLAG_OPEN_REPARSE_POINT` and read it with `symlink_metadata`.

## G. Ownership records and the copy path

### G1. Writing a record line to disk still holds up the folder's other files on Windows

* **Severity:** wrong result; the guide, the changelog and the release notes say otherwise.
* **Commit:** `3bc02a2`.
* **Where:** `crates/sumafile-transfer/src/journal.rs:734-741` (`FolderRecord::append`); test `a_line_written_to_disk_does_not_hold_up_the_other_files_of_its_folder` (`journal.rs:2022`).
* **What goes wrong:** the record is opened by `std` without `FILE_FLAG_OVERLAPPED`, and Windows serves every request on such a handle one at a time. While `FlushFileBuffers` runs, the other threads' `write_all` calls wait behind it in the system rather than on the Rust mutex. The test pauses before the `sync_all` call, in the program, so it passes on Linux and Windows without showing the effect.
* **Impact:** small. Only the line that records a Replace backup is forced to disk.
* **Proposed fix:** flush through a second handle from a separate `CreateFile` on the record (not `DuplicateHandle`, which shares the first handle's state), or remove the claim from the documents.

### G2. The rename by path and Replace run with the write handle still open

* **Severity:** wrong state on disk on some file systems (the file fails).
* **Commit:** `3f6008c`.
* **Where:** `crates/simplefile-service/src/progress/execute.rs` keeps the destination handle (`written_file`) open through `promote_leased_with_policy`; `crates/sumafile-transfer/src/staging.rs:1144-1158`.
* **What goes wrong:** before this commit the handle was closed before any rename. The fallback is for a file system that refuses the rename through the handle. Its most likely reason is the open handle itself, and the fallback renames with it still open.
* **Scenario:** a cloud mount or another third-party file system (WinFsp, WebDAV) that does not rename a file open for writing. The whole file is copied, both renames are refused, and the file fails. Replace there fails the same way.
* **Proposed fix:** hand the `File` over by value, and drop it before the fallback by path and before the Replace branch.

### G3. A name taken by the same pass in a new folder is found only after the copy

* **Severity:** wrong result (minor; no data is lost).
* **Commit:** `3f6008c`.
* **Where:** `crates/simplefile-service/src/progress/execute.rs:1223` (`copy_file_with_progress_versioned`, the skipped name check).
* **What goes wrong:** in a folder the pass created, the file's name is not looked up first. When the same pass creates a folder of that name, which happens with a case-sensitive source, the conflict shows only after the whole file was copied, and as "destination already exists" instead of "exists with a different type".
* **Scenario:** a case-sensitive source (`\\wsl$`, a Samba share, an NTFS folder with case sensitivity on) holds the file `x.bin` (40 GB) and the folder `X`, copied with the default answer into a new folder. The walker creates `X`, the file is copied in full, and the rename reports the conflict.
* **Proposed fix:** keep looking up the name in a new folder when the pass has created subfolders in it, or accept the late conflict and say so in the guide.

## Checked and found sound

Each reviewer also listed what held. In short:

* **Panics (`bd756e0`):** catching a panic per file is right; the lease, permit and handles are dropped, the lease's line is kept, the failure is not retried, and the loop after a lost worker ends.
* **Records (`bc06343`, `5413d34`, `931f7e0`):** the 1.1.5 identity form matches 1.1.5 and cannot match a new identity by mistake; skipping an unreadable line is safe; empty records are removed after a day; the Windows test fixes are right.
* **Undo (`ea920f5`):** dropping a stuck step checks that it is the same entry; the order of a merged Undo's steps is kept; an empty folder is removed only when it is empty.
* **Rename through the handle (`3f6008c`):** the `FILE_RENAME_INFO` layout, sizing and arguments are right; errors 183 and 80 are conflicts, 32 and 33 are waited out, others fall back to the rename by path; later attempts, which have no delete access, always use the checked rename by path.
* **Record locking (`3bc02a2`):** no deadlock or lock-order inversion; a slot is evicted only when nothing holds it; lines cannot reach a deleted record; a line that must reach the disk does so before the rename it protects.
* **Wire format (`8ecf375`):** the Rust encoder and the C# encoder and decoder agree on `untransferred`; the JSON form, the schema and the goldens match; the FTP/SFTP plugin's progress is unaffected; skips, renames and moved folders are counted once.
* **Attributes and streams (`aa2f277`, `2b299bc`):** `FILE_BASIC_INFO` is used as documented; every handle has the access its queries and sets need; the `FileStreamInfo` buffer, its errors and its parsing are right; streams are written before the flush, the checksum and the attributes, so read-only comes last.
* **Names (`fb6c9e0`):** the partial name with `.state` fits in 255 units; cut names cannot collide, because the hash is of the full path; the suffixes that recovery and the filters look for are kept; a retry finds the same partial file.
* **Volumes (`023063d`):** `subst` to a share, nested `subst`, mapped drives, verbatim and plain paths, share names in another case and device paths resolve correctly or fall back to "different".
* **Bandwidth group (`fbd45fe`):** no lock cycle; a removed limit, a dropped member and a cancel end a wait within 25 ms; one task alone is still paced at its limit.
* **Per-file count:** the pinned count in `progress/bench.rs` (Query 5 on Windows, 4 elsewhere with one Stat) matches the code.
