## 1. Executive summary

The shell is in good shape at the hygiene level: async handlers are funnelled
through a guard, background callbacks are marshalled, navigation and preview
loads are token-guarded, pure logic sits in Core with tests, and the 10,000-file
smoke run passes. The defects are concentrated at four seams, and most findings
below are instances of one of these root causes:

1. **One shared cancellation slot (`_utilityCts`) couples ~15 unrelated flows.**
   Settings save, Quick Look, Properties, checksums, folder metrics, Git
   fetch/pull/push, duplicate scans, Open With discovery and rename all call
   `BeginUtilityOperation()`, which cancels whoever was using it last. Result:
   Settings edits silently discarded (C3), a running duplicate scan vanishes when
   you rename a file (T1), a Git push is cancelled by clicking Reveal (P3).
2. **No app-wide dialog gate.** 21 inline `ContentDialog`s share one XamlRoot;
   the profile manager nests a second dialog from an unguarded `async void`
   click, which throws and, because `App.OnUnhandledException` re-throws
   everything except cancellation, **terminates the process** (C2). Queued
   transfer conflict prompts fail the transfer when any other dialog is open (T3).
3. **Keyboard accelerators mark keys handled before checking text focus.** Bare
   `Tab`/`Space`/`Backspace`/`Delete`/`F2` are registered on the root grid and
   always set `Handled = true`; Delete, Shift+Delete, F2, Ctrl+Z have no
   text-input guard at all. Pressing Delete inside the omnibar can trash the
   selected files; Tab cannot move focus between controls (S3/S4/C6).
4. **Focus-change side effects discard the user's input.** The omnibar re-syncs
   itself from the workspace on `LostFocus`, so clicking its own "Run" button
   runs the *reset* text, not what was typed (S1); the path-bar suggestion
   flyout steals focus and ends the edit (S2).

Beyond those, the most important individual findings are:

## 3. Cross-cutting root causes

1. **Shared `_utilityCts`** (C22; instances C3, T1, P3, C8, C9). One fix
   pattern: a CTS per logical operation or per dialog instance, cancelled on that
   dialog's/window's `Closed`, plus an `IDisposable` scope.
2. **Dialog policy** (C2, C15, T3, P20, T2). Twenty-one inline `ContentDialog`s,
   no "dialog open" gate, dialogs anchored to `Content.XamlRoot` regardless of
   which window has focus, and a `TransferProgressWindow` that activates itself.
   Combined with `App.OnUnhandledException` re-throwing, any double-open is a
   process exit unless the caller happens to be inside `RunUiActionAsync`.
3. **Accelerator handling** (S3/C6, S4, C15, S5). Decide *then* mark handled;
   one central text-safe set; scope bare keys to the file lists.
4. **Focus side effects** (S1, S2, F16, S27). `LostFocus` re-sync and
   focus-taking flyouts discard in-progress input; focus is not restored after
   overlays close.
5. **Physical-pixel window sizing** (C7, S12, P5, P25). Seven `AppWindow.Resize`
   calls; the smoke harness already shows the correct `RasterizationScale`
   pattern.
6. **UI-thread affinity of XAML image objects** (F2, F3, P27). `ConfigureAwait
   (false)` and `Task.Run` paths construct `BitmapImage` off-thread; blanket
   `catch {}` hides it.
7. **Static strings that mirror dynamic state** (S6/C4/C5, S8, S19 collapse flags,
   C19 active profile, P26 pin label, S15 toggles). The data exists; the UI copy
   is not derived from it.
8. **"Replace everything" collection refreshes** (F4, P15, P19, S9) reset
   selection and scroll.
9. **Silent degradation** (T17, P14, P16, F12, C14, S7). `catch { return
   false/[]/null; }` and hidden/no-op items leave users without feedback.
10. **Two parallel implementations that drift**: ListView vs
    `DetailsFileListView` (F4, F7, F10, F15, F21) and Primary vs Secondary pane
    views, which are verbatim copies (S18/F28).

## 4. Usability and accessibility assessment

**Strengths.** Dual-pane and tab semantics are coherent and tested; the
command palette, shortcut editor (recorder, conflict detection, import/export),
workspace profiles and the preview pane's pin/rail model are genuinely good;
destructive core flows (trash, discard, remote delete, bulk rename) are confirmed
and mostly undoable; the toolbar overflow planner keeps the omnibar usable at
narrow widths (verified at 1,000/1,280/1,920 px in the smoke run).

**Gaps that affect everyday use.**

- Keyboard-only use is impaired: Tab traversal is swallowed (S3), focus is lost
  after the palette/menus (S27, F16), Details has no marquee (F10), type-ahead
  ignores digits (F9), and Delete/F2/Ctrl+Z fire from inside text boxes (S4).
- Three overlapping text inputs (omnibar, "Find in folder", "Filter list") with
  an undocumented prefix grammar (S26); the omnibar's own Run button is broken
  (S1).
- Feedback: InfoBars vanish within ~75 ms (S7), Status Center never says
  "Done" (S8), palette no-ops (C14), hidden menu items (F11), silent drop
  rejection (F12), silent partial enrichment (F24), truncated transfer text
  with no tooltip (T16).
- Long operations without progress/cancel: Quick Look on folders, folder
  metrics (C9), archives (T7), remote connect/test (P6), git commands (P3),
  rename apply (P13).
- Settings: modeless, multi-instance, data-losing (C3, C16), DPI-clipped (C7),
  shallow grouping and search (C18), no Light theme (S23), theme not applied
  to secondary windows (X1).
- Destructive actions without confirmation: duplicate-checker trash (T6), smart
  folder delete, clear recents, status-center cancel (S17), history Retry as the
  default button (T9), conflict dialog Enter = cancel transfer (T8).

**Accessibility.** The main window is partially covered (file lists, toolbar,
palette and most sidebar buttons carry names), but: zero `AutomationProperties`
in all nine dialog XAMLs and `ProgressPanel` (T14); icon-only buttons without
names in the pane header, sidebar, Remote and Git windows (S16, P10); toggle
state not exposed on Git/Preview/Pin/collapse buttons (S15, S16, P26); sort
state and resize grips invisible to assistive tech (F22); row names set on the
inner control rather than the focused container (F22); high-contrast palette
collapses muted/primary and selected/hover (X2); Tab traversal broken (S3).

## 5. Organization assessment

- `MainWindow` is 35 partials (~13,900 lines of `MainWindow*.cs`) over one bag
  of ~60 mutable fields; divider logic lives in `MainWindow.Transfer.cs`, sidebar
  section toggles in `FileListEvents.cs`, dead Git code in
  `InspectionDialogs.cs` (S19, T23, C23).
- The UserControl split (`SidebarView`, `PrimaryToolbarView`, pane views) is
  pass-through: every named element is re-exported as a public property and every
  event re-raised, so it adds indirection without encapsulation (S19).
  `PrimaryPaneView` and `SecondaryPaneView` (XAML and code-behind) differ only
  by `Grid.Column` and initial visibility (S18/F28); every pane fix must be made
  twice and `MainWindow` carries paired `OnPrimary…/OnSecondary…` handlers and
  ternaries.
- Process-global static hosts (`ColumnLayoutHost`, `FileListViewHost`,
  `FileListHorizontalScrollHost`, `FileListThumbnailHost`) couple rows to the
  window; each `FileRowView` subscribes to four static events on `Loaded` (F28).
- Command plumbing is well designed (one catalog, one alias table, one handler
  map, 83/83 palette ids routable) but ids are string literals in ≥8 files with
  no consistency tests (C21), and the two routers have different fall-through
  rules (C1).
- Dialogs are built three ways with 22-delegate constructor injection (T24);
  secondary windows copy the same chrome code (P25).
- Dead code accumulates from earlier refactors: `ProgressPanel`,
  `TransferViewModel`, `AboutDialog`, `RunGitAsync`, legacy `AdvancedRename`
  API, `RefreshView`, `GetSelectedEntries`, `CloseDualPaneFromUiAsync`,
  `OnClearTagFilter`, `AutoCollapseTree`, the permanently hidden "Close left
  pane" button (S20, T22, P24, C12, C23).
- No TODO/FIXME/HACK markers anywhere in App or Core; the build is warning-free;
  the Core/App boundary is respected for navigation, search, rename, transfers
  and settings normalisation. The weaknesses are concentration and duplication,
  not hygiene.
